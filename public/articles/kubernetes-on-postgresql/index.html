Kubernetes on PostgreSQL

Abstract. In May 2026 the lab's Kubernetes control plane could not stay up. Its embedded etcd datastore lived on a virtual disk backed by one SATA hard drive shared with every other virtual machine on the host. Under control-plane load, etcd reported requests taking about thirty seconds, and the control plane restarted roughly every seventy-five seconds. Moving the virtual disks to an iSCSI array, together with turning off a source of heavy watch traffic, ended the crash loop, but under a heavy installation etcd's request durations still peaked at seconds. Our decision record judged that margin too thin to build on, and we replaced etcd with kine, which serves the etcd API from a SQL database, backed by the lab's PostgreSQL server and authenticated with client certificates over mutual TLS. This article tells that chronology from the decision record and from the notes and commits made at the time, describes the design that resulted, and explains what it changed about recovery: restoring the cluster now begins with restoring a database.

This is one article in a series. The overview describes the lab as a whole and the constraints it works under.

Context

The lab runs one Kubernetes cluster, built with RKE2. In early May 2026 it had a single control-plane node and two workers, all virtual machines on the lab's one Proxmox host. By default RKE2 keeps the cluster's state in etcd, embedded in the control-plane node.

etcd is sensitive to storage latency. It commits every change to a write-ahead log and waits for the disk to confirm the write before acknowledging it, and requests queue behind those commits. Leadership is built on top of the datastore. The RKE2 server process runs its own controllers under a leader-election lease held in the datastore, and it must renew that lease before a deadline; when it cannot, the process exits. The controller manager and the scheduler hold leases of their own, but they run as separate pods, and losing one restarts that pod, not the server. A slow datastore therefore becomes a crashing control plane. Our decision record took as working thresholds fsync latency consistently under about 100 milliseconds, with leader elections triggered past about 500 milliseconds. Those figures describe etcd's own Raft elections among several members. Our cluster's etcd had a single member, so the failure we saw ran through the RKE2 server's lease instead.

The cluster also had a purpose beyond the lab. We were designing a container platform for university production, which would run on a shared virtualization cluster where the same kind of latency variance is plausible. We wanted its control-plane state in a database that we, and the database administrators we work with, already know how to back up, monitor, recover to a point in time, and eventually make highly available.

Constraints

The design had to fit the lab as it was, not as we might have wished it to be.

  • One spinning disk under everything. The hypervisor's virtual disks sat on one SATA hard drive, thin-provisioned and shared by more than twenty-five virtual machines. The host has limited room for faster local drives, and adding one would have treated the symptom without changing the design.
  • Network block storage was available. A Synology array already served iSCSI to the hypervisor, so virtual disks could move off the local drive without new hardware.
  • Older silicon. The hypervisor's processor supports the x86-64-v2 instruction set but not v3. PostgreSQL 17 from the vendor's repository would not run on it, so the database server uses PostgreSQL 16 from the distribution, and we build pgBackRest from source.
  • The datastore cannot live inside the cluster it serves. The control plane needs its datastore before it can run anything, so the database has to run outside the cluster.
  • One operator, one database engine. We already run PostgreSQL and expected production to use it. A second database engine would be one more system to patch, back up and understand.

Design

kine in place of etcd

kine is a shim that implements the etcd v3 API on top of a SQL database. RKE2 includes it. When a node's configuration names an external datastore, RKE2 disables embedded etcd and starts kine instead, and every control-plane node points at the same database. There is no etcd cluster initialization and no etcd member join, because the servers hold no datastore of their own. The API server talks to kine as if it were etcd, and kine turns each request into SQL.

The effect is to move the storage-sensitive work out of the control plane and into PostgreSQL, a system designed to commit transactions durably and to recover from crashes, and one whose behavior under load we can observe with ordinary database tools.

The database

The datastore is a dedicated virtual machine running PostgreSQL 16, with its data on a dedicated virtual disk on the iSCSI-backed storage. The Ansible role that builds it is generic and multi-tenant: a tenant is a role, a database and its access rules, declared as variables. kine was its first tenant. The identity service's database and many cluster applications' databases have joined it since, which is why the overview calls it the lab's shared database.

Certificates, not passwords

The control plane authenticates to PostgreSQL with mutual TLS. Each control-plane node holds a client certificate issued by the lab's internal certificate authority through the ACME protocol. The certificate's subject is the node's own DNS name, because ACME validates a name by reaching the machine that claims it. PostgreSQL accepts the cluster's connections only over TLS, with certificate authentication, and it maps the certificate's name to a database role through a pattern in its user-name map, so any control-plane node's certificate maps to the same role. No database password exists for this connection. The certificate and its key are readable only by root on the node.

Mapping by pattern, instead of creating one database role per node, means a control-plane node can be added or replaced without any change on the database side. That property mattered later in the month.

Headroom for leader election

On 10 May, during the iSCSI work and the day before the datastore change, we lengthened the leader-election timings of the controller manager and the scheduler from the Kubernetes defaults (a 15-second lease, a 10-second renewal deadline and a 2-second retry period) to 60, 45 and 5 seconds, and they remain in place with kine. A slow datastore response now has to last much longer before either component gives up its lease. The change gives those two components headroom; it does not govern the RKE2 server's own lease.

Backups by the database's own tool

Because the cluster's state is rows in a PostgreSQL database, it is protected by the same mechanism as every other tenant. pgBackRest archives the write-ahead log continuously and asynchronously, takes a full backup weekly and a differential backup on each of the other six days, keeps two full backups and seven differentials, compresses with zstd, and encrypts on the client with AES-256 before anything leaves the lab. The repository is in Backblaze B2, whose server-side encryption is enabled as well. There is no separate etcd snapshot schedule to maintain, because there is no etcd.

Alternatives we rejected

Option Why we did not choose it
Keep etcd and buy faster disks Limited room for local drives; it treats the symptom, not the cause; it does not match the production environment we were designing for
MySQL or MariaDB through kine kine supports both, but we run PostgreSQL and expected production to use it; a second engine adds maintenance for nothing
SQLite through kine Gives up any path to high availability; kine's SQLite mode is meant for single-node edge clusters
Run the database inside the cluster The control plane needs the database before it can start any workload

What went wrong

The crash loop on local SATA

Under any substantial controller load (a Rancher installation, a cert-manager rollout, even the agents' watch streams), etcd reported single requests taking about 30 seconds. Those were request durations, not disk writes: read requests queued behind consensus commits that were themselves waiting on the disk. On a quiet system the disk answered an fsync in about 4 milliseconds; under sustained writes it took seconds. The RKE2 server could not renew its own lease in time, and it exited with leaderelection lost roughly every 75 seconds, restarted and failed again. Its restart count climbed from zero to 136 within minutes, and the cluster never reached a steady state.

We first tried memory, raising the control-plane node from 16 to 24 GB and each worker from 16 to 32 GB. It changed nothing. We also found a second source of load: the watch streams of Cilium's Hubble flow-visibility components were pushing etcd's read times past the RKE2 server's lease deadline. On 10 May we turned Hubble off.

iSCSI, and the margin that remained

On 10 and 11 May we moved the cluster's virtual disks from the local drive to the iSCSI array. Hubble was turned off in the same two days, so the improvement that followed has more than one cause. The controller-manager and scheduler timings also changed then, but they do not govern the lease whose loss stopped the RKE2 server. etcd's request durations fell from more than 30 seconds to under a second, with readings of about 456 and 503 milliseconds. The crash loop ended: our notes from the time record the three nodes ready and no further restarts. Under the write storm of a Rancher installation, though, request durations still peaked at 4.4 seconds, far above what etcd's guidance expects.

The move had its own failure. The disk-move command for the two workers was cut off partway through a script. A cleanup step then removed the disk entries from the virtual machines' configurations, which left nothing to reattach, and the disk files were deleted. Both workers lost their disks. We created empty disks and reinstalled both workers over the network through the provisioning system. Getting them back into the cluster took more than six hours of trial and error. A rejoining node must first be cleared from the control plane, including the password record the control plane keeps for it, and a skipped step fails quietly with a rejected node password or a duplicate node. That session produced a step-by-step reinstall runbook. The other lesson we recorded was narrow and concrete: before removing a disk entry, confirm that the configuration still references a disk that exists.

The decision

The decision record judged the remaining margin too thin to build on. It names the Rancher installation's load on iSCSI-backed etcd as the trigger, and it puts the iSCSI-backed fsync latency at about 650 milliseconds, roughly six times its own target; that figure is the record's estimate, not a benchmark result. It also had a reason beyond the lab: the production platform we were designing for would face the same kind of latency variance. On 11 May 2026 we moved the cluster's datastore to kine on PostgreSQL. The decision record is dated the same day. After the change, the three nodes reported ready, kine's table was filling, and the RKE2 server had not restarted. The first successful pgBackRest full backup of the new database ran that evening: it took about two minutes and stored 66.8 MB of data as 12.8 MB after compression, and write-ahead log archiving began pushing segments continuously.

What we learned

Measure the property the failure depends on. Our decision record named fsync latency as the cause without a measurement taken the way etcd's own hardware guidance recommends. On 14 May we added a weekly benchmark modeled on that guidance: small synchronous writes, each followed by a data sync, with the latency percentiles exported to Prometheus. The first run, on the iSCSI-backed virtual machines, made the point. The control-plane virtual machine's 99th percentile was 4.6 milliseconds, but its 99.9th percentile was 202 milliseconds and its worst write took 832 milliseconds. The database virtual machine showed 6.5 milliseconds, 56 milliseconds and 1.27 seconds. The 99th percentile looked healthy. Consensus protocols and lease deadlines feel the tail.

Put the sensitivity where it is cheapest to absorb. etcd turns a slow disk into lost leadership and process exits. PostgreSQL turns a slow disk into slow queries, which kine reports as warnings. Neither makes the disk faster, but the second failure mode degrades long before it crashes, and it can be watched with tools we already use.

Write down the condition for reversal. The decision record names what would make us undo it: kine's slow-query warnings consistently above two seconds under steady-state load. When we recorded it, those warnings were near zero per hour at idle, with occasional spikes during bursts of reconciliation. The same week, we built a separate test cluster on embedded etcd to check whether the trigger the decision record names, a Rancher installation on iSCSI-backed storage, actually reproduces. No result from it was recorded. The decision therefore rests on the margin argument, not on a reproduced failure, and the stated reversal signal is what lets it be revisited on evidence rather than on mood.

Separating the datastore from the control plane made the control plane replaceable. On 25 May we moved the control plane from its virtual machine to a bare-metal server, while the cluster kept running. The new server joined using the shared database, the old node was drained and deleted, and the workers rejoined the new server. Workloads stayed on the workers throughout. Because the database maps any control-plane node's certificate to the same role, the change touched only the cluster's own configuration and none of the database's.

The trade-offs are real, and we accept them. There are now two failure domains to keep healthy, the cluster and the database, where there used to be one. Until the database is replicated, it is a single point of failure for the control plane, protected by continuous archiving rather than by redundancy. kine's emulation of the etcd API is not exact, and some rare watch behaviors can differ from etcd's.

Current state

The lab runs one cluster, and since 25 May 2026 that cluster has hosted Rancher itself. A separate single-node management cluster, which had stayed on embedded etcd, was retired the same day. Rancher, whose installation produced the highest request durations recorded on iSCSI, now runs inside the cluster it manages, and its state is stored through kine in PostgreSQL.

The control plane is one bare-metal server. The database and the workers are virtual machines on the hypervisor. If the hypervisor were lost, the control-plane machine would still exist, but the cluster would not run until the database had been restored and the workers reprovisioned. The written restore order reflects this. The database comes back before any Kubernetes work begins, and the restore is checked by confirming that kine's table holds rows. Then the control plane starts and connects to the datastore at boot, the workers rejoin, and Rancher returns with its state already in place. One pgBackRest restore brings back every tenant database on the server, the cluster's included.

The recovery point for cluster state is the recovery point of the database: minutes, because the write-ahead log is archived continuously and kine's steady stream of writes keeps segments turning over. A highly available datastore becomes a database change: replacing one PostgreSQL server with a replicated cluster, without re-architecting RKE2. A multi-node control plane remains deliberately deferred.
