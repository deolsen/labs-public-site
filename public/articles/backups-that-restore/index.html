Backups that restore

Abstract. The backups this article describes go off-site to Backblaze B2 through two tools. pgBackRest protects the shared PostgreSQL server with continuous WAL archiving and scheduled full and differential backups. restic protects host file systems and, through jobs that run inside the Kubernetes cluster, application data on block storage for the services that have backup jobs. Both encrypt their repositories on the client before anything leaves the lab. This article describes that design and the failure that reshaped it. In June 2026 we moved application configuration volumes from NFS to iSCSI block volumes. The host-level restic job could not see the new volumes, so it went on backing up the copies left behind on NFS, and it reported success every night. For nearly two months the live data had no backup, while our own documentation said it did. The jobs we added on 1 August 2026 nearly repeated the mistake: their first version produced backups that contained no databases and still succeeded, and only a restore exposed it. The rule that came out of it is a per-job dump assertion. The file-level jobs count the database copies in each new snapshot and fail, before pruning anything, if any database the dump step captured is missing; the one job that dumps a database server fails if its dump is implausibly small.

This is one article in a series. The overview describes the lab as a whole and the constraints it works under.

Context

The lab runs on one hypervisor, beside a network storage array and a few bare-metal servers. Losing the hypervisor means rebuilding everything it ran, and losing the storage array means losing every virtual disk and block volume on it. A backup kept inside the lab protects against neither, so the backups this article describes are written to object storage outside it.

Two kinds of state need protecting, and they need different tools. The first is the shared PostgreSQL server. It holds the Kubernetes cluster's datastore, the identity service's database, and the databases of many cluster applications, each as a separate tenant. Copying the files of a database that is being written to is at best a best-effort backup, and the cluster's datastore changes constantly, so it needs a tool that understands PostgreSQL's write-ahead log. The second is everything else: configuration and state on host file systems, user files on the NFS gateway, and the configuration volumes of applications running in the cluster. Much of that last group is small SQLite databases, which carry a household's history (what was watched, what was saved, how each service is set up) and cannot be downloaded again.

Constraints

  • Off-site by default. The lab has one of everything that matters, so a backup that stays in the lab shares the fate of what it protects.
  • Encrypted before it leaves. The object store should see only ciphertext, encrypted with keys the operator holds.
  • Older silicon. The hypervisor supports the x86-64-v2 instruction set but not v3. The PostgreSQL project's own pgBackRest packages are compiled for v3 and will not start on it.
  • Block volumes with no snapshots. The storage array's CSI driver, as deployed, ships without snapshot support, so the cluster cannot take a volume snapshot and back up a clone of it.
  • Volumes attach to one node. Application volumes are read-write-once: each is attached to the node that runs its application, and to no other.
  • One operator. There is no second person to notice a backup that quietly stops protecting anything. Left alone, such a backup is found when someone needs it.

Design

Two tools, one destination

Both tools encrypt on the client with AES-256 before upload, and the object store's own server-side encryption is enabled underneath. The credentials each tool uses are read from HashiCorp Vault when Ansible configures the host or deploys the chart, as the secrets article describes.

PostgreSQL: pgBackRest

pgBackRest runs on the database server. PostgreSQL hands each completed WAL segment to pgBackRest, which pushes it to the object store asynchronously from a local spool, with four parallel processes. A full backup runs every Sunday and a differential backup runs on each of the other six days. Uploads are compressed with zstd and encrypted with AES-256-CBC under a cipher passphrase held in Vault. Retention keeps two full backups and seven differentials, and WAL is kept back to the oldest full backup that remains, so the repository supports point-in-time recovery across that window.

A single pgBackRest stanza covers the whole PostgreSQL cluster. Because every tenant lives on one server, one restore brings back every tenant database at once, including the Kubernetes datastore.

Two details come from the constraints. We build pgBackRest from source, pinned to a release, because the PostgreSQL project's binary needs an instruction set our hardware lacks; our decision record (ADR-004) found no x86-64-v2 build in that repository, and EPEL does not package pgBackRest at all. And the Ansible role runs pgbackrest check after creating the stanza, which fails unless PostgreSQL's WAL is actually reaching the repository, so a configuration that looks right but archives nothing does not pass that step.

Host file systems: restic

Three hosts run a restic client installed by an Ansible role: the infrastructure server, the NFS gateway, and the database server, where file-level backup is a coarse safety net beside pgBackRest. Each host writes to its own restic repository, so one host's backups and locks never touch another's. A systemd timer runs the backup daily, and a second timer is scheduled weekly to forget and prune old snapshots. Retention keeps the last 3 snapshots and 24 hourly, 14 daily, 4 weekly, 12 monthly and 3 yearly snapshots.

What goes into each backup is chosen per host, and so is what stays out. The largest exclusion is the media library on the NFS gateway, many terabytes that can be downloaded or ripped again. User content beside it, such as music, photos and books, is kept.

Application data on block storage: one job per application

Application configuration volumes live on iSCSI block storage, which no host-level backup can see. For the services that have backup jobs, they are backed up by restic running inside the cluster, as one Kubernetes CronJob per application, defined in the same Helm chart that deploys those applications.

Each job mounts its application's volume directly. Because the volume is read-write-once and already attached to the application's node, the job carries a required pod-affinity rule that places it on the same node as the application. We confirmed both ways that without the rule, the scheduler can place the job elsewhere, and the pod then fails to attach the volume. With no volume snapshots available, mounting the live volume beside the running application is the only way in, which makes the next rule essential.

Live databases are never copied as files. An init container runs SQLite's online backup API against each database, read-only, and writes a consistent copy to a scratch volume. restic then backs up that copy together with the rest of the volume, and the raw database files and their write-ahead logs are excluded from the file sweep. The online backup copies pages, so it works even for an application that ships its own SQLite build with custom collations. Where a job discovers databases by name rather than from a list, a file named like a database that turns out not to be SQLite is copied as-is instead of failing the job. One application keeps its data in a MariaDB server instead of SQLite, and its job takes a logical dump over the network in a single transaction, because copying a running InnoDB data directory file by file is not crash-safe.

Each application has its own repository, as each host does, so the jobs never contend for a repository lock. They use the same credentials as the host backups and keep the last 3 snapshots and 14 daily, 4 weekly, 12 monthly and 3 yearly snapshots. They run daily, after the host-level run, so the object store is not written by both at once. If the cluster was down at the scheduled time, a job still runs if the cluster comes back within two hours, instead of skipping the day.

What is kept follows one rule: back up what is irreplaceable. Anything a rescan or a download regenerates is excluded, however long regenerating it would take. For the media server, that took the configuration volume from about 125 GB, mostly generated thumbnails, transcodes and downloaded metadata, to well under one gigabyte: its library database, its preferences, and little else. A derived search index is not backed up at all, because it is rebuilt from the database of the application it indexes.

The rule: a job proves its dumps landed

Every one of these jobs checks its own output before it trusts it. The dump step fails the job outright if a database it was told to capture is missing, or if any database it finds cannot be captured. It then records how many databases it captured. After the upload, the restic step counts the database copies in the new snapshot. If fewer are present than the dump step recorded, the job fails, and it fails before it prunes, so the previous good snapshot is kept. The MariaDB job takes a different form of the same check: it refuses a dump of a kilobyte or less, since a server that answers but returns nothing useful would otherwise produce a backup that looks complete.

The rule exists because of the two failures that follow.

What went wrong

The backup that protected nothing

Until June 2026, application configuration lived on NFS, and from late May the NFS gateway's restic job captured it every night. The SQLite databases on those volumes were the cause of repeated application stalls and restarts, because NFS locking does not suit SQLite. Between 7 and 19 June we moved the configuration volumes to iSCSI block volumes provisioned through the storage array's CSI driver.

The host-level backup did not follow. It backs up paths on the NFS gateway, and the live data was no longer there. The job went on backing up the copies the migration had left behind, which no longer changed, and it reported success every night. Thirteen volumes were affected. On 1 August 2026 the job was still capturing copies about eight weeks old. For one application, the newest database in the backup was dated 7 June, while the live database was dated 30 July.

The documentation made it worse. Our backup plan still said this data was covered. Had we needed it, we would have found the gap in the middle of a restore.

The fix that backed up no databases

On 1 August we added the per-application jobs. The first version excluded raw database files with an unanchored pattern, matching any file whose name ends in .db. That pattern also matched the consistent copies the dump step had just written. The jobs reported success and stored backups that held no databases at all.

The job's success said nothing about it. A restore did: the first restore test from the object store reported that it had restored a single item of zero bytes. We anchored the exclusions to the application's live volume, so that they can no longer match the dump directory. Then we added the snapshot count described above, so that a file-level job cannot report success when a database it captured is missing from the snapshot.

The check needed debugging of its own. Its first version listed only the top of the dump directory, so it counted zero for applications whose databases sit in subdirectories, and it failed backups that were good. It now counts across the whole snapshot listing.

After those changes, all twelve jobs completed with their checks satisfied. We then restored one application from the object store into a fresh pod. SQLite's integrity check passed, and the restored database held the same record counts as the live one.

A tool that would not start

The pgBackRest role began with the vendor's package. On the hypervisor's older processor, every invocation of that binary exited at once, reporting that the CPU's instruction-set level was lower than required. The project's repository had no build for that level, and EPEL did not package pgBackRest. The role now builds a pinned release from source with the system compiler and installs it beside the system's own binaries, and every task and timer calls it by its absolute path. The first full backup with the source-built binary completed the same evening, 11 May 2026.

What we learned

A job's success is a claim about the job, not about the data. The host backup succeeded for eight weeks while protecting none of the data it was meant to protect, and the first replacement succeeded while storing no databases. In both cases every signal we had said all was well. The per-job assertion moves the check from "did the command exit cleanly" to "is the thing we care about in the snapshot", and it is placed so that a failure keeps the last good snapshot instead of pruning toward a bad one.

Moving data is a backup change. The migration in June was a storage change, made for good reasons. None of the commits that made it mentions backups, and the backup was defined by paths on another machine. The new jobs live in the same Helm chart as the volumes they protect, so the backup of each volume is defined next to the volume itself.

Documentation is a claim, too. The backup plan said the data was covered. It had not been updated when the data moved. A statement of coverage needs the same scrutiny as the configuration it describes.

A restore found what the job could not. The empty backups were found by restoring, not by reading logs or counting snapshots, and we restored once more before trusting the fix. The per-job assertion now catches the specific failure that restore found: a snapshot missing a database the dump step captured. It does not prove that any other part of a snapshot will restore.

The check is code, and code has bugs. The first version of the assertion failed good backups. A check that is wrong in that direction is noisy rather than dangerous, but it is still wrong, and it had to be tested against real backups like everything else.

Current state

The shared PostgreSQL server is protected by pgBackRest 2.58.0, built from source, with continuous asynchronous WAL archiving, a full backup every Sunday and a differential backup on the other six days, keeping two full backups and seven differentials. One stanza covers every tenant database.

Host file systems on the infrastructure server, the NFS gateway and the database server are configured for daily restic backups, one repository per host, with a weekly prune timer.

Application data on block storage for the services that have backup jobs is backed up by twelve CronJobs configured in the cluster, using restic 0.19.1: eleven file-level jobs, one per application volume, and one logical database dump. Each file-level job dumps its SQLite databases through the online backup API and fails before pruning unless the new snapshot contains every database the dump step captured. The database-dump job fails on a dump of a kilobyte or less. The rule described here belongs to these twelve jobs, as the commit of 1 August 2026 introduced them.

Every backup this article describes is written to Backblaze B2, outside the lab, into a restic or pgBackRest repository encrypted on the client.
