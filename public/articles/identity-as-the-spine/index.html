Identity as the spine

Abstract. The lab's colleague-facing services sign people in through one identity layer, and are designed so that access to them is granted through a governance process rather than by editing a service. Some operator tools still use their own local logins. Three products divide the work. An Active Directory domain is the authority for the lab's own accounts. Keycloak federates that directory, brokers the university's SAML identity provider, and issues the tokens services trust. midPoint holds the access model: which applications exist, which roles grant access to them, and which grants need a person's approval. This article describes that design. It then tells the failures that shaped it. The most instructive was a read-only directory setting that, for two weeks in August 2026, made every brokered sign-in by a person whose directory account carried a different first name fail on every retry, and what the UNSYNCED edit mode changes: Keycloak may edit its own copy of the user and still never writes to the directory.

This is one article in a series. The overview describes the lab as a whole and the constraints it works under.

Context

The lab's users come from two places. Lab accounts, the operator's among them, live in the lab's directory. Colleagues live at the university, which runs its own single sign-on service on Shibboleth; they have no account in the lab's directory and should not need one.

Keycloak serves OpenID Connect and SAML to the lab's services. It organizes users, clients and identity sources into realms. The lab's realms grew one application at a time, and most of them carry their own copy of the directory federation. As colleagues began to sign in, each realm that admitted them also needed its own connection to the university, so the same identity sources were being configured again and again.

The lab is also where we try identity-governance designs before proposing them at work. That is why midPoint is part of the design: access should be requested, approved, recorded and revoked in one place, and the services should only ever see the result.

Constraints

  • The directory is authoritative, and Keycloak never writes to it. Account data flows from the directory into Keycloak, never the other way.
  • The university controls its identity provider. The lab's brokers use a registration the university had already issued. The university decides which name-identifier formats it will issue and which attributes it releases, and we cannot change either.
  • Colleagues are external. They authenticate with their university accounts and must not receive directory accounts in order to use a lab service.
  • Configuration is code, and grants are data. Ansible is meant to own realms, clients, identity providers and federation settings; midPoint grants access inside those realms.
  • One operator approves. Every request for a colleague tool that requires approval is reviewed by hand, so the approval path has to be reliable.

Design

The three products have separate jobs. The directory says who a lab account is. Keycloak proves who is signing in and tells services which groups that person holds. midPoint decides which groups a person should hold, and changes them only through its own policy.

Directory federation

Keycloak's LDAP federation with the directory imports its users into each federated realm, alongside any local users. Each federation has an edit mode. The lab's default is READ_ONLY, which means Keycloak refuses any change to an imported user. UNSYNCED means Keycloak keeps changes in its own local copy of the user and never writes them to the directory. Realms that broker another identity provider, or that write to the user during sign-in, use UNSYNCED for the directory federation; other realms stay READ_ONLY. The reason is the main failure in this article.

The hub realm

Since 26 July 2026 the lab has had a hub realm, built so that a person has one account however they arrive. It federates the directory and brokers the university's SAML provider and Google.

Newer services sign in at the hub: error tracking, observability, and the lab's documentation site among them. Older application realms predate it and still federate the directory or broker the university themselves, which is why the fix described below had to cover more than one realm. The design's end state is one realm per application, each brokering only to the hub, so that every identity source is configured once.

The principle is to authenticate broadly and authorize narrowly: anyone with a lab or university account can prove who they are, and what they can reach is decided by the groups midPoint grants.

Brokering the university's SAML provider

Keycloak acts as a SAML service provider toward the university under a registration the university had already issued. Keycloak signs its authentication requests. The university signs its responses and encrypts each assertion to the registered certificate, so Keycloak holds that key pair twice, once for signing and once for decryption.

We request a persistent name identifier. The university issues it as an opaque, pairwise value, stable for one person at one service provider, which makes it a good link and a poor username. The username therefore comes from an attribute that carries the person's familiar login name. The university does not release a given name for every account type, so a second mapper fills the first name from the display name, which it always releases.

Option Why we did not choose it
Transient name identifier It changes at every sign-in, so each sign-in would create a new user
Username from the name identifier The persistent identifier is an opaque value, unusable as a username
Username from the scoped principal name Viable; the shorter login name was preferred
Make the first name optional We preferred names that are always populated

A separate realm for external collaborators

One realm exists only for invited external collaborators. It has no directory federation at all. It brokers the university and Google, and its first-sign-in flow is link-only: a brokered sign-in succeeds only if it matches an account that already exists, and an unmatched identity is rejected rather than registered. The accounts it matches are created by midPoint, disabled until an approval enables them.

Governance in midPoint

midPoint holds three layers. Each lab application is a service object in its inventory. Each application has its own access roles, and most roles, once assigned, grant a group in Keycloak through midPoint's Keycloak connector. A small set of business roles bundles the combinations people commonly need, such as a baseline for external collaborators, while individual roles remain requestable one at a time.

Approval is a reusable metarole. It carries one policy rule: adding an assignment of any role that assigns this metarole opens an approval case with a single stage. Nothing is provisioned while the case is open. The approver is one person, the operator.

One role is meant for internal people only. In midPoint 4.9 a role's own policy rule has no selector for the person holding it, so the rule is a global policy rule: it refuses assignment of that role to anyone marked as an external collaborator.

Governing the hub without owning it

midPoint governs the hub through a link-only resource. Accounts there belong to the directory federation, to the identity brokers, or to the Keycloak configuration in the repository, so the resource is designed never to create, delete or disable one. The only change it is meant to make is to add or remove the group memberships that hand-assigned roles contribute, and the connector sends each such change with a same-value write of the full user.

Two rules make that safe. The first is correlation. midPoint links a hub account to one of its users only when two attributes agree, and never to a system account. Anything less leaves the account unlinked.

The second is revocation. Unassigning a role removes exactly the group that role granted. Groups that midPoint did not grant, such as those a broker mapper or the directory supplied, are left in place, and the account itself is kept and stays linked. The configuration behind this is relative assignment enforcement, with the account's existence pinned to true. Why that combination is needed is told below.

What went wrong

An approval that never fired

In June 2026, while codifying midPoint's live configuration into the repository, we found that the approval metarole was not working. Its policy rule sat in an inducement of order two, which applies the rule one level too far down, to the user rather than to the role being assigned. The rule never matched a role assignment, so approval never fired through any channel: the administrative API, self-registration, or a person's own request. We moved the rule to an ordinary order-one inducement, the pattern Evolveum documents for policy metaroles. An end-to-end test then confirmed that an assignment opens an approval case and that nothing reaches Keycloak until the approver approves.

The university provider, end to end

On 23 July 2026 we pointed the collaborator realm's broker at the university's production Shibboleth service, replacing a local stand-in; the hub, built three days later, brokered the same provider. The configuration was not re-derived for the real provider, and the first end-to-end test, on 27 July, found three latent problems. The provider refused the unspecified name-identifier format we requested. It encrypted assertions to a key Keycloak held only for signing, so decryption failed. And once the format question was settled, the username mapping produced an opaque string. We fixed all three on the hub that day and confirmed a complete sign-in, then codified those fixes and the display-name fallback for both brokering realms and recorded the reasoning in a decision record.

The sign-in that failed forever

Between 3 and 17 August 2026, brokered university sign-ins failed where the realm also federated the directory in READ_ONLY mode. The person saw a generic error from the identity provider step, and trying again produced the same error.

The cause was one unhandled write. Because the lab's brokers force-synchronize profile data, on every brokered sign-in Keycloak compares the email and names in the incoming assertion with the local user and writes back whatever differs. The university supplies the first name from its display name. The directory holds a given name in a different form. For a person with both a directory account and a university account, the two first names differed, so Keycloak tried to set the first name on a read-only federated user. Its federated storage threw a read-only exception, and the throw abandoned the flow before Keycloak saved the link between the university identity and the local account. Nothing was saved, so the next attempt began from exactly the same state and failed the same way. Eleven failures were recorded in those two weeks, and every one was the same write: the first name. Throughout the period, every university sign-in by the operator, who has both kinds of account, failed this way.

The fix was to set the directory federation's edit mode to UNSYNCED. The name is easy to misread. UNSYNCED does not give Keycloak write access to the directory. It makes Keycloak's imported copy of the user editable and leaves the directory untouched, which is what the constraint required all along.

The same change set two more realms to UNSYNCED. They reach the university through another realm over OIDC, but brokered sign-in runs the same write, and they had not failed only because nobody had brokered into them recently.

We also wrote the rule down as a test. As written, it renders the federation configuration from the role's real settings and fails if any realm that federates the directory and brokers an identity provider would come out READ_ONLY. It also fails if a realm with no broker would come out writable, which was meant to keep the fix from widening into blanket write access. The templates render and the linters pass, and the defect exists only at runtime against a live identity provider.

The same write without a broker

Separately, three days later, the rule turned out to be broader than the one we had written down. A realm with directory federation and no broker at all served an OAuth sign-in whose path writes to the user after a successful password check. A correct directory password produced a bare HTTP 500 with nothing in the server's log and no stored event, while a wrong password was handled normally and a local user signed in without trouble. The realm's event store had been disabled, which is why the failure left no trace. The fix was the same edit mode, and a configuration run confirmed that the provider came out UNSYNCED. Whether a realm brokers was never the real question. The question is whether anything in its sign-in path writes to the user.

The revocation that did not revoke

In October 2026 the hub resource, as first committed, could not revoke: unassigning a role would not remove its group. We corrected it the same day.

The resource had used positive assignment enforcement, chosen so that an unassigned account could never be deleted, and positive enforcement keeps the values a removed role contributed. Relative enforcement removes them, but on its own it turns the loss of an account's last assignment into a decision to delete the account, which skips the group removal and fails against the disabled delete capability. Pinning the account's existence to true resolves both: the account is always meant to exist, and the removed role's group is taken away. A render test checks this configuration, and each of nine deliberate breakages of it makes the test fail.

What we learned

A read-only store is a property of the directory, not of the sign-in. In April 2026, while first connecting a SAML application to a directory-federated realm, we hit the same read-only exception from a different write: a persistent name-identifier format makes Keycloak store a per-application identifier on the user. We switched that client to send the username as its name identifier, which needs no per-user write. That fixed the instance and left the class in place. Four months later the class came back as a sign-in failure that repeated without end. The general rule is that any realm whose sign-in path writes to the user needs a writable local copy, and UNSYNCED provides one without touching the directory.

Guard the invariant, not the instance, and state the invariant precisely. A test written against the real configuration aims to catch the next realm that gains a broker on the workstation instead of in a colleague's browser. It is only as good as the rule it encodes, and our first statement of the rule, keyed on brokers, was narrower than the behavior it was meant to guard against.

Test the real path, in both directions. Two of the failures here were invisible until something exercised the whole path: the approval that never fired, and the latent problems with the production university provider. A grant is only tested when both assignment and removal have been watched reaching the service.

In midPoint, ownership is not metadata. In July 2026 we routed approvals to each application's owner, so that delegating an application later would mean changing one owner. Owning a role in midPoint also routes approval of changes to that role. Ansible's routine updates to the roles started queuing as approval cases, and the roles could no longer be maintained as code. We reverted to the single fixed approver. Delegation waits until a second owner actually exists.

When linking accounts midPoint did not create, correlate narrowly. Linking an account to the wrong person is a security failure. Leaving one unlinked is an inconvenience the operator can resolve by hand. Requiring two attributes to agree keeps the failure on the inconvenient side.

Current state

Every realm but the external collaborators' realm federates the directory. That federation is READ_ONLY by default and UNSYNCED on every realm that brokers an identity provider or writes to the user during sign-in.

The hub realm federates the directory and brokers the university's Shibboleth service and Google. Newer services sign in there, and the remaining application realms are meant to move behind it.

midPoint 4.9 holds the application inventory, per-application access roles, business roles, the approval metarole with one approver, and the internal-only assignability rule. Since October 2026 it also governs group membership on the hub through the link-only resource, linking an account only when two attributes agree, and revoking exactly what it granted.
