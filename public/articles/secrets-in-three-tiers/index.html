Secrets in three tiers

Abstract. The lab keeps its secrets in three stores, and our decision record places each secret by one question: does whatever consumes it need it before the runtime secret store is running? Provisioning credentials are encrypted with SOPS and committed to git. A small set of configuration secrets, including the credential Ansible uses to reach Vault, are encrypted with Ansible Vault. Most other secrets, service credentials among them, live in HashiCorp Vault, which keeps its state in cloud object storage and unseals itself through a cloud key-management service. The keys that open the first two tiers, and Vault's own recovery material, are kept in an encrypted break-glass bundle stored outside the lab. This article describes that design and what auto-unseal changes about Vault's recovery keys: they authorize a small set of privileged operations, but they cannot unseal Vault or decrypt its data. It then tells four failures, each since corrected in the code, in which a recovery path looked present but was not: a TLS certificate that expired with nothing to renew it, a break-glass password file that no bundle had ever contained, a helper that the bundle did not carry, and recovery keys that were stored only inside the Vault they recover.

This is one article in a series. The overview describes the lab as a whole and the constraints it works under.

Context

The lab is rebuilt from code. Terraform and a provisioning system create the machines, Ansible configures them, and Helm charts deploy the cluster workloads. Each step needs credentials at a different moment. The provisioning system's API token is needed before any lab service exists. A service's administrator password is needed when Ansible configures that service. A backup key or a client secret is needed whenever a service is deployed, and it should be possible to change it without a commit.

Our decision record (ADR-002) concluded that a single secret store cannot serve all three moments. It rejected keeping everything in Vault because rebuilding from nothing would then need Vault running before Ansible could deploy it, while Vault itself is deployed by Ansible. It rejected keeping everything encrypted in git because every rotation would be a commit, and no value could change without touching the repository. The record set out to give each secret the store whose availability matches the moment it is needed, and to make the loss of each store a recoverable event with a known procedure.

Constraints

  • One operator. One person provisions, configures and recovers the lab. Any procedure that depends on a second keyholder, or on remembering an undocumented step, is a procedure that fails.
  • No circular dependency during a rebuild. Nothing needed to bring a store back may live only inside that store.
  • Encrypted at rest in the repository. The configuration repository is the source of truth for the lab. Secrets can sit in it only as ciphertext, and the keys that decrypt them never enter it.
  • We run the authority. We did not want a hosted secrets service to be the single source for fundamental operations. The runtime store is software we run, even though its storage and its seal are cloud services.
  • The hypervisor can be lost. The lab runs on one hypervisor, so the runtime store's data and its unseal mechanism have to survive the loss of that hardware.

Design

The routing rule

Our decision record places each secret by one question: does its consumer need it before HashiCorp Vault is up? If yes, it belongs in one of the two git-backed tiers. If no, it belongs in Vault.

Tier Store Unlocked by Contents
1. Provisioning SOPS-encrypted YAML beside the Terraform that uses it An age private key on the operator's workstation The provisioning system's API token, the hypervisor's API token, the directory-join password
2. Configuration Ansible Vault-encrypted variables in the repository The Ansible Vault password The credential Ansible uses to sign in to HashiCorp Vault, and a few host and database credentials
3. Runtime HashiCorp Vault, key/value version 2 An AppRole login that issues a short-lived token Service administrator and directory credentials, backup and object-storage keys, OpenID Connect client secrets, archive encryption passwords

The second tier is smaller than its name suggests. At the end of April 2026 we replaced most per-role Ansible Vault files with lookups into HashiCorp Vault at apply time, so service credentials now live in tier 3, and tier 2 keeps little beyond the credential that reaches Vault.

The tiers form a chain. Tier 1 can be opened with nothing but a file on the workstation, so Terraform can run before any lab service exists. Tier 2 holds the credential that opens tier 3. Tier 3 holds the values that change.

Runtime secrets reach services through deployment

Ansible reads runtime secrets through a small lookup plugin that we maintain. The plugin runs on the operator's workstation, signs in to Vault with the AppRole credential from tier 2, receives a short-lived token, and reads the value. Ansible then renders it into the service's configuration or into a Kubernetes Secret. On the common path, a running service never talks to Vault; each deployment reads from it.

This shapes what rotation means. Rotating a runtime secret is a write to Vault followed by a re-run of the role that consumes it. It needs no commit and no change to any encrypted file, which is the property the runtime tier exists to provide.

The Ansible Vault password has two paths

The Ansible Vault password itself has two ways in. Day to day, a helper fetches it from HashiCorp Vault, so no person or agent is prompted for it. The original helper, which decrypts a GPG-encrypted copy of the password, is kept as the break-glass path, because it is the only one that works with HashiCorp Vault unreachable. During a rebuild that is the likely case, so the restore runbook overrides the default and names the GPG helper explicitly.

That arrangement deliberately keeps one secret in two tiers. The decision record names duplication across tiers as its signal that a boundary is wrong. We read that signal as applying to authoritative copies: the GPG-encrypted password is a recovery copy that keeps the Ansible Vault password available when tier 3 is not.

HashiCorp Vault with KMS auto-unseal

Vault runs as a single container on one infrastructure host. Its storage backend is cloud object storage, and its seal is a cloud key-management service (AWS KMS). Neither lives on the lab's hardware, so losing the host does not lose the data or the seal: a rebuilt server that points at the same storage with the same cloud identity unseals with its data intact. It terminates TLS itself, with a certificate from the lab's internal certificate authority, and it is not published at the lab's public edge.

Vault encrypts everything it stores with a key that is itself protected by a root key, and it starts sealed: it cannot read its own data until the root key is available. With the default Shamir seal, operators supply a quorum of unseal-key shares after every restart. With auto-unseal, Vault asks a trusted device or service to decrypt the root key at startup. For us that means a restart, a host reboot, or a certificate reload brings Vault back unsealed with no person involved. That property is what makes it safe to reload Vault automatically when its certificate is renewed, as described below.

The trade is a strict dependency. HashiCorp's documentation is direct about it: if the seal mechanism becomes unavailable, Vault cannot be accessed until it is available again, and if the seal key is permanently deleted, the cluster cannot be recovered, even from backups.

What recovery keys can and cannot do

When Vault is initialized with auto-unseal, it does not hand back unseal keys. It returns recovery keys, split with Shamir's secret sharing. Ours are five shares, and our runbook records a quorum of three.

Recovery keys are an authorization mechanism. A quorum of them is what Vault requires for the operations that would otherwise need unseal keys:

  • Generating a new root token, for example when the root token is lost and directory sign-in is unavailable.
  • Rekeying, which can replace either the recovery-key shares or the key behind Vault's barrier. Replacing the recovery-key shares is the rekey target named recovery, which applies only with auto-unseal or a hardware security module; the default target is the barrier key.
  • Seal migration, where recovery keys are supplied when the old seal is an auto seal.

They cannot decrypt the root key. If the key-management service is unreachable, or Vault's cloud credentials have been revoked, Vault stays sealed, and no number of recovery keys changes that. If the key is disabled, Vault unseals on its next start after the key is re-enabled. If the key is deleted, the data in object storage is unrecoverable, with or without recovery keys. AWS KMS does not delete a key immediately: it imposes a waiting period of seven to thirty days, during which deletion can be canceled. A key pending deletion cannot be used in any cryptographic operation, so during that period Vault stays sealed on its next start. Canceling the deletion leaves the key disabled, so Vault unseals only after the key is also re-enabled.

So recovery keys protect against losing the root token, not against losing the seal. Recovery from a seal failure means restoring access to the key. For that reason the break-glass bundle carries Vault's cloud identity as well as its recovery keys.

The break-glass bundle

A shell script assembles the keys and recovery material that a lost workstation or infrastructure host would otherwise take with it, and encrypts them into one file:

  • the operator's GPG keyring, whose secret keys remain protected by their own GPG passphrases inside the bundle;
  • the SOPS age key, which opens tier 1;
  • both Ansible Vault password helpers, the GPG-encrypted password file, and the credential the day-to-day helper uses;
  • the internal certificate authority's state;
  • Vault's root token and recovery keys;
  • Vault's cloud identity: the credentials and identifiers for its object storage and its KMS key.

The script encrypts the archive symmetrically with GPG, using AES-256 and an iterated, salted passphrase derivation, under a passphrase of at least sixteen characters that the operator holds in memory, with a fallback kept separately from the bundle. The procedure keeps copies outside the lab and shreds the local working copy once they are placed and a decryption check has passed. The bundle is deliberately not stored in the lab's off-site object storage, because reaching that storage depends on credentials the bundle holds.

A companion script decrypts a bundle into a temporary directory without restoring anything. It imports the GPG keys into a throwaway keyring, checks the age key's format, validates the certificate authority's archive with the same installer a restore uses, in a mode that installs nothing, confirms that the break-glass password file really decrypts, and checks Vault's recovery fields by name without printing any value. When that password file's key is protected by a passphrase and no terminal is available to unlock it, the script reports the file as unverified and exits with a status of its own instead of passing it. Its last line states its limit: a bundle that decrypts is not proof that the credentials inside still work. The procedure calls for rebuilding the bundle after setup, after rotating the GPG, SOPS or certificate-authority keys it carries, and quarterly, and for verifying each new bundle before the old copies are replaced.

Alternatives we rejected

Option Why we did not choose it
Everything in HashiCorp Vault Rebuilding from nothing needs Vault running before Ansible can deploy it
Everything in SOPS Every rotation becomes a commit
Everything in Ansible Vault The same drawbacks as SOPS, with weaker support for multiple recipients
A hosted secrets service as the single source An external dependency for fundamental operations, and authority outside the lab

What went wrong

Each of these failures has the same shape: a recovery path existed on paper, and something quietly kept it from working.

The certificate that nothing renewed

Vault was deployed at the end of April 2026. Its Ansible role issued a TLS certificate from the internal certificate authority with a 90-day lifetime, and the task was guarded so that it ran only when no certificate existed. Nothing renewed it. By late July the certificate had expired, silently, and every client that reached Vault over TLS failed: the workstation's session helper, Ansible, and the deployments that read from it.

On 29 July we added a daily systemd timer, with jitter and catch-up after downtime. It checks whether fewer than thirty days remain, issues a fresh certificate if so, and reloads Vault. We chose a fresh issuance over a renewal because it produces a fixed lifetime every time and still works if the certificate has already expired, which a renewal refuses. The reload recreates the container, and that is safe only because of auto-unseal: Vault comes back unsealed with nobody present.

A break-glass path that no bundle had ever contained

The first bundle script, written in May, captured the GPG-based Ansible Vault helper and was meant to capture the encrypted password file it decrypts. It found that file by searching the helper's text with a pattern that expected a path beginning with a slash. The helper wrote the path relative to the home directory, so the match produced a path that did not exist, the existence check failed, and the script printed a mild note and moved on. On 2 August we found that the file had almost certainly never been in any bundle. Every bundle contained the break-glass helper but not the encrypted password it needs, so the path that was supposed to work with the lab down could not have worked at all. The fix expands the home-directory forms, and the message now names the path it looked for and states the consequence.

A helper the bundle did not carry

The same day, we made the Vault-backed helper the default for Ansible Vault. The GPG helper depended on a passphrase cache that was wiped whenever the GPG agent restarted, and each restart surfaced as a password failure. The change introduced a second gap: the bundle carried only the GPG path, so a restore would have produced an Ansible configuration naming a helper that was not there. The same fix captures both helpers and the credential the new one needs. The restore runbook gained a warning at the top. With Vault down, the default fails, and the failure looks like a wrong password rather than an outage, which is a hard thing to diagnose in the middle of a recovery.

Recovery keys stored inside the Vault they recover

When Vault was initialized, its root token and recovery keys were stored in Vault itself. Auto-unseal never asks for them, but it also means they can be read only while Vault is healthy. In the scenarios where they matter most, such as a lost host, a seal problem, or a lost root token with directory sign-in down, they were out of reach. On 8 October we extended the bundle to export the root token, the recovery keys and Vault's cloud identity, printing only field names as it goes. The verification script now checks those fields by name.

What we learned

A recovery path is not real until something checks it. All four failures were silent. A certificate was valid until it was not, a script printed a gentle note instead of failing, and a configuration change left the bundle a step behind the workstation. A missing file now produces a warning that names the file and the consequence. The verification script checks Vault's recovery fields by name and says plainly that decrypting is not recovering. And the certificate is renewed by a timer instead of by memory.

Auto-unseal moves the risk; it does not remove it. It removed a person from every restart, and it is what makes reloading Vault after a certificate renewal safe. In exchange, the lab's ability to read its own secrets depends on one key in a cloud service. Recovery keys do not hedge that dependency. Access to the key does, and the bundle carries Vault's cloud identity for that reason.

Convenience paths and recovery paths should be different paths. The Vault-backed helper is the right default for unattended work. It is also the path most likely to fail during the disaster it would be needed for. Keeping the GPG path, and saying in the script and the runbook why it must not be tidied away, preserves the property the tiers were designed for.

The decision record's question applies to recovery material too. It was not asked of Vault's own root token and recovery keys until October, although their consumer, by definition, needs them when Vault is not available.

Current state

The three tiers are as described above. Tier 1 holds provisioning credentials encrypted with an age key. Tier 2 holds Ansible's credential for Vault and a few host credentials under an Ansible Vault password that reaches Ansible through HashiCorp Vault day to day, or through GPG when Vault is down. Tier 3 is configured as HashiCorp Vault 1.18.4, auto-unsealed by a cloud KMS key, with its storage in cloud object storage, read by Ansible through an AppRole that issues short-lived tokens.

Vault's TLS certificate is configured with a 90-day lifetime and set to be reissued automatically once fewer than thirty days remain. The bundle script captures both Ansible Vault paths, the internal certificate authority's state, and Vault's root token, recovery keys and cloud identity, and its companion checks Vault's recovery fields by name. A bundle is only as current as the last time the script ran, which is why the procedure calls for rebuilding it after rotating the GPG, SOPS or certificate-authority keys, and quarterly.
