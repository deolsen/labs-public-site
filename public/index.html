The Lady Knowledge Labs home lab

Abstract. Lady Knowledge Labs runs a small private computing lab in a residence: one virtualization host, two bare-metal servers (one for the Kubernetes control plane, one for infrastructure services), a network storage array, and a residential internet connection. We use it to build and prove infrastructure designs before we propose them at work, and to run a modest set of research tools for colleagues. This page describes what the lab is for, the constraints it operates under, the principles that shape it, and its architecture in a single pass. The articles listed at the end each take one subsystem and tell its story in full: what we built, what broke, and what we changed as a result.

What the lab is, and why it exists

The lab is a proving ground for our work in university IT. Designs for that work (container orchestration, identity governance, batch computing) are built here first, run under real load, and broken here first. A design that reaches a proposal has already met real hardware, real users, and its own failure modes.

That purpose sets the bar. A lab that only demonstrates a happy path teaches little. This one is expected to carry real workloads for real people, to be rebuilt from its repository, and to record its own failures. Three kinds of work run on it:

  • Platform experiments. A Kubernetes cluster that serves as the prototype for a campus container platform's successor, an identity stack that federates a directory with a university single sign-on service, and a small batch-computing cluster for staging scheduler designs.
  • Research tools for colleagues. Collaborative LaTeX editing, Jupyter notebooks, access to language models through a single gateway, and a read-only view of the cluster. Colleagues sign in with their university accounts, and every request for access is reviewed by hand.
  • Household services. A media server and a few personal applications. They matter here because they have daily users and no tolerance for data loss, and it was their data that exposed the storage and backup failures described below.

The lab is young. Its repository began in April 2026 and held more than six hundred commits when this page was written. The configuration behind everything described here lives in that repository.

Constraints

The lab's design is mostly a response to its constraints. They are listed first because nearly every decision in the articles traces back to one of them.

One hypervisor. Every virtual machine runs on a single Proxmox host, including the database server and the Kubernetes workers. There is no live migration and no high availability at the virtualization layer. Losing that host means rebuilding everything it ran, so the rebuild path has to be written down, automated, and recoverable from backups kept somewhere else.

Older silicon. The hypervisor's processor is an Intel Ivy Bridge part, which supports the x86-64-v2 instruction set but not v3. Some upstream projects now build their enterprise Linux packages for v3, and those binaries refuse to start on this host. We build some tools from source and take others from the distribution's own repositories instead of the vendor's. Production fleets contain old hardware too, and a design that silently assumes the newest instruction set has a dependency nobody wrote down.

One bare-metal control plane. The Kubernetes control plane runs on a single physical machine, separate from the hypervisor, so the control plane's machine is not lost with the hypervisor. The cluster's state lives in the database, which is a virtual machine, so after a hypervisor loss the cluster is rebuilt by restoring that database and reprovisioning the workers. A multi-node control plane is deliberately deferred.

Shared storage over the network. Virtual machine disks and Kubernetes block volumes live on a Synology storage array reached over iSCSI. Some software, etcd and SQLite among them, tolerates network storage poorly.

A residential network. The lab sits behind a home internet connection and a home router, and most of its public names resolve to that connection; this site's own host sits behind a proxy instead. Public services must be reachable without exposing the lab's interior.

An operator behind a full-tunnel VPN. The operator's workstation often runs a university VPN that sends all traffic through the campus network, including traffic meant for the lab in the next room. Administration therefore cannot assume a local path to the lab. It has to work over a path the VPN does not capture.

One operator. There is no second administrator to remember how something works. Anything that exists only in one person's memory is, for practical purposes, already lost.

Principles

Three principles follow from those constraints. Each is reflected in how the repository is built.

Everything as code

Virtual machines are provisioned by Terraform driving Foreman, which installs the operating system over the network. Ansible configures every managed host and deploys most cluster workloads; the repository holds 16 Helm charts. Argo CD tracks a small set of charts that Ansible does not deploy, with manual sync, so drift becomes visible before anything reconciles it. Significant decisions are recorded as architecture decision records, fifteen so far, each stating the context and the alternatives that were rejected.

The reason is the single operator. A lab that can be rebuilt from its repository survives both the loss of its hardware and the fading of its operator's memory. A lab configured by hand survives neither.

Identity first

Colleague-facing services authenticate through one identity layer, and are designed so that access to them is granted through a governance process rather than by editing a service directly. Some operator tools still use their own local logins. A directory is the authority for the lab's own accounts. Keycloak federates that directory and brokers university single sign-on, so a colleague signs in with an account they already have. midPoint holds the access model: who may use which tool, which grants need approval, and which roles imply which group memberships.

Putting identity first means a new service begins by deciding who may use it and how that decision is reviewed. It does not begin by creating local accounts.

Recovery designed in

Every stateful component is meant to have a named backup mechanism and a place in a written restore order. Secrets are split into tiers; the keys and recovery material that open them are kept in an encrypted bundle outside the lab; and the cluster's own state lives in a database that is archived continuously. A job reporting success is not evidence that a backup holds what it should: the lab once had a backup job that succeeded every night while protecting none of the data it was meant to protect. The per-application backup jobs that replaced it fail when a database copy they captured is missing from the snapshot, or, for the one job that dumps a database server, when the dump is implausibly small.

The architecture in one pass

This section walks the lab from the outside in: how a request arrives, where it is served, how the caller is identified, where state lives, and how that state is protected. The diagrams name roles, not machines.

Compute

The virtualization host runs Proxmox and carries the service virtual machines, the shared database, and the Kubernetes workers. Two bare-metal servers sit beside it. One runs the Kubernetes control plane; it moved there from a virtual machine in May 2026. The other is the infrastructure server: it runs provisioning, the internal certificate authority, HashiCorp Vault, and DNS, and it is the first machine rebuilt in the written restore order. An operator workstation with a GPU serves the local language models behind the model gateway.

The cluster is RKE2 with Cilium for networking, and MetalLB announces service addresses on the local network. Rancher, which manages the cluster, runs inside it, so there is one cluster to operate and back up rather than two.

The cluster's datastore is the decision with the most history behind it, and the lab's first serious failure. RKE2 ships with embedded etcd, and etcd needs storage that commits writes quickly. The lab's virtual disks first sat on a single local SATA disk, where under control-plane load etcd requests took as long as thirty seconds, with reads queued behind commits waiting on the disk; the RKE2 server could not renew its leader-election lease and restarted roughly every seventy-five seconds. Moving the virtual disks to the iSCSI array, together with turning off a source of heavy watch traffic, ended the crash loop, but under a heavy installation etcd's request durations still peaked at several seconds, far above etcd's guidance. Our decision record judged that margin too thin to build on, and in May 2026 we replaced embedded etcd with kine, a shim that serves the etcd API from a SQL database, backed by the lab's PostgreSQL server. The control plane connects to the database over mutual TLS, presenting a client certificate issued by the internal certificate authority in place of a database password.

This design turns cluster recovery into database recovery. The control plane's state is covered by the same continuous archiving that protects the lab's other databases, and a future highly available datastore becomes a database change rather than a rebuild of the cluster.

The edge

Public web traffic arrives at a single Traefik instance running inside the cluster. Since May 2026 it has been the public TLS edge for the lab's web services. Public routes are declared in Helm charts, most of them beside the service they publish, so adding a service and publishing it are one change. Public certificates come from Let's Encrypt through DNS-01 challenges, which prove control of a domain with a DNS record rather than an inbound connection, and browsers trust them without installing anything. Inside the lab, the internal certificate authority issues the certificates for traffic between servers.

Identity

Colleague-facing services sign in through Keycloak. A central hub realm federates the directory and brokers the university's SAML identity provider. midPoint sits beside Keycloak and holds the access model: roles, approvals, and the group memberships they imply. When a request is approved, midPoint grants the corresponding group membership in Keycloak.

Brokering a production university identity provider took several iterations. In July 2026 we pointed the broker at the university's Shibboleth service, and the first end-to-end test exposed latent problems: a name-identifier format the provider refused, an encryption key that had been imported only for signing, and a username mapping that produced an opaque string. All of them were fixed and recorded in a decision record. A later failure, described below, taught us more.

Secrets

Our decision record splits secrets into three tiers, designed around one question: does the consumer need this secret before the runtime secret store is running?

Provisioning credentials are encrypted with SOPS and committed beside the Terraform that uses them. A small set of configuration secrets, including the credential Ansible uses to reach Vault, are encrypted with Ansible Vault. Service credentials and values that rotate live in HashiCorp Vault, which keeps its state in cloud object storage and unseals itself through a cloud key-management service, so a restart needs no person holding unseal keys. The keys that open the first two tiers, and Vault's own recovery material, are kept in an encrypted break-glass bundle stored outside the lab.

Data and storage

One PostgreSQL 16 server is the lab's shared database. It holds the cluster's datastore, the identity service's database, and the databases of many cluster applications, each as a separate tenant. A single database server is a single point of failure, and we accept that at this scale. It is protected by continuous WAL archiving and scheduled full and differential backups with pgBackRest, which we build from source because the vendor's packages require the newer instruction set.

Bulk files live on an NFS gateway in front of the storage array. Application databases no longer do. In June 2026 we moved application configuration volumes from NFS to iSCSI block volumes provisioned through the Synology CSI driver, after SQLite databases on network file storage proved to be the cause of repeated application stalls and restarts. Host file systems and most application volumes are backed up with restic. Both restic and pgBackRest write to Backblaze B2, encrypted by the client before upload, with the provider's server-side encryption enabled as well.

Observability

Prometheus collects host and service metrics, and Alertmanager delivers alerts to a phone through a self-hosted ntfy server, so alerting needs no outside mail relay. Since September 2026 a self-hosted SigNoz instance has also collected telemetry from AI coding-agent sessions, alongside host metrics. For instrumented sessions it shows where agent work is happening. A session reports only if it started after telemetry was configured, and sessions from one of the two agent tools can be placed by machine and time but not by project.

Reaching the lab from elsewhere

The operator administers the lab through a bastion host joined to a Tailscale network. Tailscale's encrypted tunnels travel over the public internet as ordinary traffic, so the university VPN's full tunnel does not capture them. This path has been in service since August 2026.

Failures that shaped the design

The datastore failure is told above, under Compute. Two more failures changed the design, and the articles tell both in full.

The sign-in that failed forever. In August 2026, brokered university sign-ins by people who also held a directory account failed in realms that federated the directory read-only. On every brokered sign-in, Keycloak updates the user's profile from the incoming assertion. The university supplies a first name in a different form from the directory's, so Keycloak tried to write the change to a read-only directory, threw an error, and abandoned the sign-in before saving the account link. Every retry started over. The committed change sets the federation's edit mode to UNSYNCED: Keycloak may now edit its local copy of the user, and it still never writes to the directory.

The backup that protected nothing. When application configuration moved from NFS to block volumes in June 2026, the host-level backup kept running and kept succeeding, but it was backing up the abandoned copies left on NFS. For nearly two months, thirteen volumes of live data had no backup, while the documentation said they did. On 1 August 2026 we added a backup job per application that runs beside the volume it protects, and made each file-level job fail if a database copy it captured is missing from its snapshot; the one job that dumps a database server fails if the dump is implausibly small.

The backup failure gave no signal at all, and the sign-in failure surfaced only as a generic error to the person signing in. Each fix moved the lab toward designs that fail instead of reporting success, or that cannot fail that way at all.

Reading guide

The articles below are written to stand alone. Each opens with an abstract, follows the same arc (context, constraints, design, what went wrong, what we learned, current state), and ends with references.

  • Kubernetes on PostgreSQL. The datastore chronology: an etcd crash loop on local SATA, iSCSI and less watch traffic ending it with little margin, then kine on a continuously archived PostgreSQL, authenticated by client certificates over mutual TLS. Start here if you run Kubernetes on modest or shared storage.
  • Identity as the spine. Directory federation, a hub realm, brokering university SAML, and governance with approvals in midPoint, including the read-only federation setting that broke brokered sign-in for people who also held a directory account, and what UNSYNCED changes.
  • Secrets in three tiers. SOPS at provisioning, Ansible Vault for configuration, HashiCorp Vault at runtime with KMS auto-unseal; what recovery keys can and cannot do, and why the break-glass bundle is kept outside the lab.
  • Backups that restore. restic and pgBackRest to object storage, how a move to block storage silently orphaned application backups for nearly two months, and the rule it produced: each per-application backup job fails when a database copy it captured is missing from its snapshot, or, for a database-server dump, when the dump is implausibly small.

Later releases will cover the public edge, storage, reaching a lab from behind a full-tunnel VPN, certificate management, observability for AI agents, and documentation treated as a product.
